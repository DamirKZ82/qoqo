# Развёртывание на Vercel

Репозиторий разворачивается двумя проектами Vercel из одной ветки: сайт и API
собираются по-разному и живут на разных доменах. Оба конфига лежат в репозитории,
руками в интерфейсе задаётся только корневой каталог и переменные окружения.

| Проект | Root Directory | Что получается |
| --- | --- | --- |
| `qoqo-web` | `qoqofront` | Статика Vite, отдаётся с CDN |
| `qoqo-api` | `qoqoback` | FastAPI одной Python-функцией |

## Что завести до первого деплоя

**PostgreSQL с пулером соединений.** Подойдут Neon, Supabase или свой
PgBouncer. В `DATABASE_URL` нужен адрес именно пулера: serverless поднимает
процесс на вызов, и без пулера база упрётся в лимит подключений. Приложение со
своей стороны пул не держит — на Vercel оно само переходит на `NullPool`
(переменную `VERCEL` платформа выставляет сама).

**S3-совместимый бакет** для логотипов, обложек новостей и картинок блоков:
AWS S3, Cloudflare R2, MinIO — что угодно с S3 API. На Vercel файловая система
только для чтения, а `/tmp` живёт до конца вызова, поэтому локальный диск для
загрузок там не годится. Объекты должны читаться публично — напрямую или через
CDN перед бакетом.

Регион функций стоит выбрать тот же, где стоит база: каждый запрос ходит в неё
несколько раз, и лишние 100 мс на round-trip заметны.

## Проект API

Root Directory — `qoqoback`. Остальное берётся из `vercel.json`: весь трафик
заворачивается на функцию `api/index.py`, которая отдаёт ASGI-приложение
FastAPI. Версия Python зафиксирована файлом `.python-version`.

**В `pyproject.toml` не должно быть таблицы `[project]`.** Сборщик Python,
найдя её, считает `pyproject.toml` источником зависимостей и ставит объявленное
там, а `requirements.txt` не смотрит вовсе. Таблица без `dependencies`
оборачивается функцией без единой библиотеки: `ModuleNotFoundError: No module
named 'fastapi'` и `FUNCTION_INVOCATION_FAILED` на всех путях. Список
зависимостей в проекте один — `requirements.txt`; если `[project]` понадобится,
переносить туда придётся весь список, а не держать его в двух местах.

**Framework Preset должен быть `Other`, а Build Command и Install Command —
пустыми.** Если проект завести с чужой предустановкой или прописать свою
команду установки, Vercel соберёт его как проект на Node: исходники скопирует,
а `pip install` не выполнит. Функция при этом разворачивается без библиотек и
падает при импорте — `ModuleNotFoundError: No module named 'fastapi'`, ответ
`FUNCTION_INVOCATION_FAILED` на всех путях. По ответу это неотличимо от ошибки
в коде, поэтому смотреть надо журнал сборки: там должна быть установка
зависимостей.

Переменные окружения:

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | Адрес пулера. Драйвер можно не указывать: `postgresql://…` из панели Neon или Supabase подойдёт как есть |
| `SECRET_KEY` | Случайная строка: `python -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `CORS_ORIGINS` | Домен сайта, через запятую, если их несколько |
| `FRONTEND_URL` | Домен сайта — из него собираются ссылки в письмах |
| `S3_BUCKET` | Имя бакета |
| `S3_ENDPOINT_URL` | Для AWS оставить пустым, для R2/MinIO — адрес API хранилища |
| `S3_REGION` | Регион бакета |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Ключи доступа к бакету |
| `S3_PUBLIC_URL` | Адрес, по которому файлы читает браузер: CDN или сам бакет |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | Почта для приглашений |
| `LOG_FILE` | Пустое значение: на serverless писать журнал некуда |
| `SEED_OWNER_EMAIL` | Почта администратора — заводится при первом запуске |
| `SEED_OWNER_PASSWORD` | Его пароль. Значение из `.env.example` не подойдёт намеренно |
| `DEBUG` | `false` |

Пустое значение любой переменной означает «не задано» — приложение возьмёт
значение по умолчанию. Заводить переменную заранее, оставляя её пустой, безопасно.

Файловая система здесь только для чтения, поэтому `LOG_FILE` должен быть пустым:
приложение настраивает журнал при импорте, и попытка создать каталог уронила бы
функцию целиком, ещё до первого запроса. Вывод в консоль платформа собирает сама.

Администратор заводится при первом запуске из `SEED_OWNER_EMAIL` и
`SEED_OWNER_PASSWORD` — иначе войти было бы некому: регистрации нет. Пароль из
`.env.example` не подойдёт: с ним учётная запись намеренно не создаётся, потому
что его знают все, кто видел репозиторий.

Если `SMTP_HOST` оставить пустым, письма не отправляются: ссылка на установку
пароля возвращается администратору прямо в ответе API. Для боевого контура так
делать не стоит.

`TIMEZONE`, `ACCESS_TOKEN_EXPIRE_MINUTES` и `INVITE_EXPIRE_HOURS` имеют разумные
значения по умолчанию и нужны, только если требуется их изменить. Полный список
с комментариями — в [`qoqoback/.env.example`](qoqoback/.env.example).

## Проект сайта

Root Directory — `qoqofront`. Сборка и SPA-роутинг описаны в `vercel.json`:
любой путь, под которым нет файла, отдаёт `index.html`, иначе прямые ссылки на
`/app/orders` возвращали бы 404.

Единственная переменная:

| Переменная | Значение |
| --- | --- |
| `VITE_API_URL` | Домен API без хвостового слэша, например `https://qoqo-api.vercel.app` |

Переменная попадает в сборку, поэтому после её изменения нужен передеплой, а не
только перезапуск.

## Миграции и первый вход

Миграции на Vercel не выполняются: функция живёт доли секунды и не должна
менять схему. Накатывать их нужно из CI или с локальной машины, подключаясь
напрямую к базе (не через пулер — PgBouncer в режиме transaction ломает DDL):

```bash
cd qoqoback
DATABASE_URL='postgresql+psycopg://…прямое подключение…' .venv/bin/alembic upgrade head
DATABASE_URL='postgresql+psycopg://…прямое подключение…' .venv/bin/python -m app.scripts.seed
```

Сид создаёт администратора и печатает одноразовую ссылку для установки пароля.
Ссылка собирается из `FRONTEND_URL`, так что переменную стоит выставить до
запуска сида.

## Что стоит знать про serverless

- **Холодный старт.** Первый запрос после простоя поднимает процесс и открывает
  соединение с базой — это заметно. Если критично, на Vercel есть Fluid compute.
- **Долгие запросы.** `maxDuration` в `vercel.json` стоит 30 секунд. Отчёт за
  год по большой базе в него укладываться должен, но если упрётся — считать
  такие выгрузки лучше фоново, а не поднимать лимит.
- **Локальный диск.** Всё, что записано за время вызова, исчезает вместе с ним.
  Пока `S3_BUCKET` не заполнен, загрузка логотипа формально пройдёт, а файл
  пропадёт — поэтому бакет здесь обязателен, а не желателен.
- **Список заявок на экране склада** опрашивает сервер каждые 10 секунд. Это
  постоянный фон вызовов в рабочее время — стоит держать в уме при оценке
  счёта.

## Проверка после деплоя

```bash
curl https://qoqo-api.example/api/v1/health          # {"status":"ok",…}
curl -I https://qoqo-web.example/app/orders          # 200 и index.html
```

Дальше — войти сотрудником, открыть «Настройки» и загрузить логотип: это
единственная операция, которая одновременно проверяет базу, бакет и права.
