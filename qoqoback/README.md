# qoqoback

Бэкенд системы QoQo на FastAPI: публичный API сайта и внутренняя система учёта продаж.

## Стек

- Python 3.12, FastAPI, Pydantic v2
- SQLAlchemy 2.0 (синхронный движок) + Alembic
- PostgreSQL через psycopg3
- JWT (PyJWT) + bcrypt
- ruff, pytest

> Слой БД синхронный намеренно: на Windows асинхронный psycopg несовместим с
> `ProactorEventLoop`, который asyncio использует по умолчанию. FastAPI выполняет
> синхронные зависимости в пуле потоков.

## Запуск

```bash
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
cp .env.example .env   # подставить пароль от PostgreSQL
.venv/Scripts/alembic.exe upgrade head
.venv/Scripts/python.exe -m app.scripts.seed
.venv/Scripts/python.exe -m uvicorn app.main:app --reload
```

API на http://localhost:8000, документация — http://localhost:8000/docs.

## Роли

| Роль | Что может |
| --- | --- |
| `admin` — Администратор | Всё, включая сотрудников и настройки системы |
| `director` — Директор | Все заявки и любые переходы статуса, справочники, контент |
| `accountant` — Бухгалтер | Видит все заявки, может отменить; правит справочники и контент |
| `sales_rep` — Торговый представитель | Только свои заявки: создать, отправить, отменить |
| `warehouse` — Склад | Заявки своего склада: сборка, отгрузка, доставка |

Кладовщик со складом по умолчанию видит заявки этого склада **и** заявки, где
склад ещё не указан, — иначе такая заявка не попала бы ни к кому.

### Что видит торговый представитель

Справочники — работа офиса, в меню представителя их нет. Есть «Мои точки»: тот
же экран торговых точек, но только со своими, и без права правки.

«Свои точки» — это закреплённые за ним (реквизит «Торговый представитель» в
карточке точки) и точки его маршрутов. Два признака, а не один: закрепление
могут не заполнить, а маршрут представителю всё равно выдадут — иначе он не
увидел бы точку, в которую его сегодня отправили.

Отчёты у него ограничены теми же точками: продажи его точки — его показатель,
даже если заявку оформил кто-то другой. Собственные заявки видны в любом
случае, включая точки, которые ему ещё не закрепили.

Ограничения живут на сервере (`app/services/scope.py`), а меню лишь повторяет
их: адрес запроса легко подобрать, а данные отдаёт сервер. Общие справочники —
номенклатура, контрагенты, договоры — представителю по-прежнему читаются: без
них не выписать заявку.

## Доступ сотрудников

Самостоятельной регистрации нет. Администратор заводит сотрудника
(`POST /api/v1/users`), тот получает письмо с одноразовой ссылкой и сам задаёт
пароль. В базе хранится только SHA-256 токена, срок жизни — `INVITE_EXPIRE_HOURS`.

Адрес в ссылке берётся из источника запроса: сотрудника заводит администратор,
открывший систему в браузере, — значит адрес сайта известен точно, и
`FRONTEND_URL` для этого задавать не нужно. Источник принимается только из
`CORS_ORIGINS`: иначе подделанный заголовок увёл бы ссылку с одноразовым токеном
на чужой сайт.

`FRONTEND_URL` остаётся запасным вариантом — он нужен там, где запроса нет
вовсе: в сид-скрипте и в консольной выдаче приглашения.

### Почта

Настройки почты живут в системе: «Настройки» → «Почта для приглашений».
Администратор задаёт их сам, не имея доступа к развёртыванию, — иначе завести
сотрудника без девопса было бы нельзя.

Переменные `SMTP_*` остаются запасным вариантом: если в базе сервер не указан,
берутся они. Так уже работающие установки не ломаются, а в разработке заводить
ничего не нужно.

Пароль от ящика — чужой: им пользуются, значит хешировать его нельзя. Лежит
зашифрованным на ключе, выведенном из `SECRET_KEY` (`app/core/secrets.py`), и
наружу не отдаётся никогда: в ответе только признак `password_set`. Пустое
значение при сохранении означает «оставить прежний» — иначе пароль стирался бы
при каждой правке формы. Смена `SECRET_KEY` делает сохранённое нечитаемым:
пароль вводят заново, в лог уходит понятная строка.

Кнопка «Отправить проверочное письмо» шлёт письмо себе. Почтовые серверы
отказывают по десятку причин, и узнать об этом надо до того, как приглашение не
дойдёт до нового сотрудника.

Если почта не настроена вовсе, письмо не отправляется: ссылка пишется в лог
сервера и возвращается администратору в ответе API — удобно для разработки.

Выпустить ссылку из консоли:

```bash
.venv/Scripts/python.exe -m app.scripts.invite user@example.com
```

## Статусы заявки

```
Черновик → Новая → В сборке → Собрана → Отгружена → Доставлена
              ↘ Отменена ↙
```

Переходы проверяются на сервере дважды: разрешён ли переход в принципе
(`STATUS_TRANSITIONS`) и разрешён ли он этой роли (`ROLE_TRANSITIONS`).

## Отчёты

`GET /api/v1/reports/sales` — итоги за период, сравнение с предыдущим таким же
по длине периодом и динамика с шагом `day`, `week` или `month`. Периоды без
заявок остаются в ряду с нулями, иначе провал в продажах на графике читался бы
как обрыв данных.

В ряду только дата начала периода: подпись собирает клиент средствами `Intl`
на выбранном языке, поэтому названия месяцев на сервере не нужны.

`GET /api/v1/reports/breakdown` — тот же период в разрезе: `outlet`,
`counterparty`, `sales_rep`, `nomenclature`, `category`, `warehouse`.
`GET /api/v1/reports/breakdown/export` отдаёт разрез целиком файлом CSV
(разделитель `;` и BOM — иначе Excel ломает кириллицу). Заголовки в файле пишет
сервер, поэтому у выгрузки есть параметр `lang` — `ru` или `kk`.

`GET /api/v1/reports/top` — лидеры продаж, по умолчанию по номенклатуре: топ
продаваемых товаров. Разрез у топа свой, не общий с таблицей разреза: чаще
всего нужно видеть ходовые товары и одновременно смотреть разрез по точкам.

Показатель переключается: `order_by=amount` — по деньгам, `order_by=quantity` —
по объёму. «Топ продаваемых» читают двояко, и для продуктов разница
существенная: дорогая позиция обгоняет по выручке то, что расходится тоннами.
На наших данных бедро идёт первым по сумме (76 320 ₸ за 48 кг), а желудки —
первыми по объёму (68 кг за 60 520 ₸).

Доли и «хвост» всегда считаются от денег, даже когда топ построен по объёму:
доля в килограммах смешивала бы штуки с килограммами и складывала несравнимое.

Прирост к прошлому периоду считается по всем строкам прошлого периода, а не
только по попавшим в топ: иначе позиция, вылетевшая из десятки, дала бы рост
от нуля.

Продажами считаются заявки в работе: черновики и отменённые не учитываются.
Суммы и количества берутся по строкам заявок, поэтому в любом разрезе
складываются в один и тот же итог.

Отчёты открыты администратору, директору, бухгалтеру и торговому
представителю. Складу отчёты закрыты. Представитель видит цифры только по
своим точкам — см. «Что видит торговый представитель».

## Продукция на сайте

Раздел «Наша продукция» на сайте (`/products`) и карточка товара
(`/products/<адрес>`) собираются из номенклатуры. Отдельного справочника для
витрины нет намеренно: товар вёлся бы в двух местах и однажды разошёлся бы сам
с собой.

В карточке справочника появились реквизиты витрины: «Показывать на сайте»,
фотография, описание, состав, фасовка, срок годности и условия хранения.
Публикуется только отмеченное — в номенклатуре есть служебные позиции, которым
на витрине не место.

Адрес карточки заводится сам при загрузке фотографии — транслитерацией
наименования. Карточка открывается и по идентификатору: товар без фотографии
тоже должен быть доступен.

`GET /api/v1/catalog` отдаёт опубликованные товары, сгруппированные по группам
номенклатуры, `GET /api/v1/catalog/<адрес>` — одну карточку. Оба открыты без
авторизации: это страницы для покупателя. Цен и остатков в ответе нет.

Загрузка фотографии — `POST /api/v1/catalog/<id>/image`, доступна тем же ролям,
что правят справочники. Принимаются JPEG, PNG и WEBP до 5 МБ.

**На serverless нужен бакет.** Пока `S3_BUCKET` пуст, файл сохраняется на
локальный диск, а он там не переживает вызов: фотография загрузится и пропадёт.

## Справочники и обмен с 1С

У всех справочников первичный ключ — UUID, и его можно задать при создании.
При синхронизации с 1С сюда кладётся `Ref_Key` соответствующего объекта, поэтому
идентификаторы не придётся перематчивать.

Организации, Подразделения, Склады, Единицы измерения, Номенклатурные группы,
Номенклатура, Контрагенты, Типы торговых точек, Торговые точки, Договоры.

Удаления нет — элемент помечается неактивным (`is_active = false`), потому что
на него могут ссылаться проведённые документы.


### Единицы измерения из ОКЕИ

При заведении единицы работает подбор из ОКЕИ: он заполняет код, наименование,
полное наименование и код по ОКЕИ разом. Смысл в коде — при обмене 1С
сопоставляет единицу именно по нему, а не по названию, и «кг», набранное
руками, с «Килограмм» из 1С не сойдётся.

Классификатор лежит в коде (`app/data/okei.py`), а не в базе: он не меняется во
время работы, и заводить ради него таблицу с миграцией незачем. Набор рабочий,
не полный: масса, объём, тара, длина, время — то, чем измеряют товар в
торговле. Добавить недостающую единицу — дописать строку в кортеж.

Поиск идёт по коду, обозначению и названию сразу: человек помнит либо «166»,
либо «кг», либо «килограмм». Отбирает сервер, а не браузер — иначе список
фильтровался бы по подписи «166 — Килограмм», в которой «кг» не встречается, и
верное совпадение пропадало бы.

`GET /api/v1/classifiers/okei?search=` отдаёт набор.

## Язык

Интерфейс переводится на клиенте: сервер отдаёт коды (`status`, `role`,
`dimension`, `category`), а подписи к ним собирает фронтенд. Поля `*_title` в
ответах остаются на русском — они для внешних потребителей API и обмена с 1С.

Единственное исключение — выгрузка CSV: её текст пишет сервер, поэтому
заголовки колонок и названия разрезов заведены на двух языках в
`app/schemas/report.py`.

## Контент сайта

Главная страница собирается из секций (`content_blocks`): тип блока, порядок,
видимость и `JSONB` с содержимым. Состав полей блока меняется без миграций.
Новости и акции — отдельная сущность с датами и публикацией.

## Загруженные файлы

Логотипы, обложки новостей и картинки блоков по умолчанию лежат на диске в
каталоге `MEDIA_ROOT` и раздаются самим приложением по `/media`. Если заполнить
`S3_BUCKET`, файлы уходят в S3-совместимое хранилище, а в базе сохраняется
абсолютный адрес — фронтенд одинаково понимает оба варианта.

На serverless бакет обязателен: локального диска, переживающего вызов, там нет.
Подробнее — в [DEPLOY.md](../DEPLOY.md).

## Остатки на складах

Остаток — это сумма движений (`stock_movements`), а не отдельно хранимое число:
так он не может разойтись с документами. Движения создаёт проведение документа,
отмена проведения их удаляет.

Виды документов: поступление, списание, инвентаризация и отгрузка. У
инвентаризации нет знака — движение считается как разница между фактом и тем,
что числится, поэтому расхождение само спишется или оприходуется. Отгрузка
создаётся автоматически при переводе заявки в «Отгружена» и списывает
фактически собранное количество, а не заказанное.

Свободный остаток = учётный минус резерв. В резерве числятся заявки в статусах
«Новая», «В сборке» и «Собрана»: они уже заняли товар, но ещё не отгружены. Без
этого один и тот же товар пообещали бы двум точкам.

`GET /api/v1/stock/orders/{id}/check` отвечает, хватит ли остатка на заявку.
Собственный резерв заявки при этом возвращается обратно в доступное количество,
но только если заявка действительно попала в резерв: черновик ещё ничего не
занял, и списывать его на себя нельзя.

## Взаиморасчёты

Долг не хранится числом: он считается как отгруженное минус оплаченное. Долг
создают заявки в статусах «Отгружена» и «Доставлена» — пока товар не уехал,
платить не за что.

Срок оплаты берётся из отсрочки по договору (`payment_days`), поэтому просрочка
вычисляется, а не вводится руками. Без договора отсрочки нет: оплата считается
по факту отгрузки.

Оплата, привязанная к заявке, гасит именно её; общая оплата разносится от самых
старых отгрузок к новым — так же, как это делает бухгалтер. Иначе просрочка
висела бы на давно закрытой отгрузке.

`GET /api/v1/settlements` — долги по контрагентам с просрочкой и остатком
кредитного лимита. `GET /api/v1/settlements/counterparties/{id}` — акт сверки:
разбивка долга по срокам и перечень отгрузок с оплатами.

Кредитный лимит проверяется при отправке заявки на склад. Лимит берётся
максимальный по договорам контрагента, нулевой означает «без ограничения».
Директор и администратор ограничением не связаны, но чужие черновики им не
видны, поэтому на практике заблокированную заявку разблокируют, подняв лимит в
договоре.

Взаиморасчёты доступны бухгалтеру, директору и администратору.

## Оборачиваемость запасов и сводка руководителя

`GET /api/v1/reports/stock-turnover` считает, за сколько дней распродаётся
средний остаток. Средний остаток — полусумма на начало и на конец периода:
общепринятое упрощение, считать по каждому дню дороже, а результат почти тот же.

Коэффициент — расход, делённый на средний остаток; «дней на продажу» —
длительность периода, делённая на коэффициент; «запас, дней» — на сколько
хватит текущего остатка при том же темпе. Сортировка от самых медленных: именно
в них заморожены деньги. Позиции без движения дольше 30 дней помечаются
залежавшимися.

`GET /api/v1/reports/dashboard` — сводка руководителя одним запросом: продажи за
день, неделю и месяц с изменением к предыдущему такому же периоду, долг и
просрочка, заявки в работе, позиции без свободного остатка, залежавшийся товар
и выполнение маршрутов за сегодня. Каждая тревога ведёт на экран, где с ней
можно что-то сделать.

## Возвраты от клиентов

Проведение возврата делает две вещи сразу: приходует товар на склад складским
документом вида «Возврат» и уменьшает долг контрагента. Если сделать только
одно, разойдётся либо остаток, либо взаиморасчёты.

Возврат гасит долг наравне с оплатой, но в балансе учитывается отдельным полем
`returned`: иначе по отчёту не понять, сколько денег реально пришло.
Привязанный к заявке возврат уменьшает именно её долг, непривязанный — с самой
старой отгрузки.

Цена берётся из связанной заявки, а при её отсутствии — текущая цена товара:
возврат должен уменьшать долг ровно на ту сумму, за которую отгружали.

Причины «Истёк срок» и «Брак» помечают товар как непригодный к продаже. На
склад он всё равно приходуется — иначе остаток не сойдётся, — а списывается
отдельным документом.

Отмена проведения возвращает и остаток, и долг к исходному состоянию.

## Импорт из файла

`/api/v1/imports/{kind}/preview` разбирает файл и возвращает, что получится,
ничего не записывая; `/apply` применяет. Двухшаговость намеренная: загружать
сотни строк вслепую и потом выяснять результат — верный способ испортить
справочник.

Форматы — XLSX и CSV. CSV читается с BOM и точкой с запятой: именно так его
сохраняет Excel с кириллицей. Дробная часть принимается и через запятую.
Заголовки колонок сопоставляются без учёта регистра, образец отдаёт
`/imports/template/{kind}`.

Совпадение ищется по коду, поэтому повторная загрузка того же файла обновляет
записи, а не плодит дубли. Строки с ошибками пропускаются, остальные грузятся —
из-за одной опечатки не приходится перезагружать весь файл.

Начальные остатки заводятся инвентаризацией: она выравнивает остаток до
указанного количества, поэтому повторная загрузка не удваивает запас. На каждый
склад создаётся свой документ.

## Маршруты и визиты

Маршрут задаёт дни недели, а не конкретные даты: иначе план пришлось бы
переписывать каждую неделю. У точки маршрута хранится порядок обхода и дни
посещения по ISO (1 — понедельник, 7 — воскресенье); пустой список означает
«каждый день».

`GET /api/v1/field/plan?day=` разворачивает план на день. Визит в точку, которой
в маршруте на сегодня нет, тоже попадает в план: представитель мог заехать по
звонку, и в отчёте это должно быть видно.

Отметка о визите сохраняет координаты и сразу считает расстояние до точки по
формуле гаверсинуса. Потом координаты уже не проверить, а именно они отличают
визит от галочки из машины: порог задаётся `VISIT_MAX_DISTANCE_M` (по умолчанию
300 метров). Отсутствие координат — не нарушение, а «проверить нечем»: у точки
может быть не заполнена карта, а представитель мог отказать браузеру в доступе
к геолокации. Такие визиты показываются отдельно, а не как обман.

Один визит на точку в день: повторная отметка правит ту же запись. Маршруты
составляют администратор и директор, ходит по ним представитель; чужой план
виден только руководителям.

Геолокация в браузере требует HTTPS — на localhost работает, в бою нужен
сертификат.

## Telegram-бот

Сотрудник привязывает свою учётную запись к боту из панели пользователя:
система выдаёт одноразовый код и ссылку `t.me/<бот>?start=<код>`. Пароль и почта
в Telegram не передаются, код живёт `TG_LINK_CODE_TTL_MINUTES` минут и
срабатывает один раз. Один чат принадлежит одному сотруднику: при повторной
привязке прежняя снимается, иначе уведомления уходили бы не тому.

Токен бота задаётся в `TG_TOKEN`. Если он пуст, привязка в интерфейсе не
предлагается, а отправка сообщений молча пропускается.

Приём сообщений в разработке — опросом, отдельным процессом:

```bash
.venv/Scripts/python.exe -m app.scripts.telegram_bot
```

В боевом контуре опрос не нужен: включается вебхук, и Telegram сам стучится в
приложение.

```bash
python -m app.scripts.telegram_webhook status          # что стоит сейчас
python -m app.scripts.telegram_webhook set https://qoqo.kz
python -m app.scripts.telegram_webhook delete          # вернуться к опросу
```

Секрет вебхука лежит в `TG_WEBHOOK_SECRET` и приходит от Telegram заголовком
`X-Telegram-Bot-Api-Secret-Token`, а не в адресе: адреса запросов пишут в свои
журналы и nginx, и облачные балансировщики, поэтому секрету в адресе не место.
Команда `set` без настроенного секрета предложит готовую строку для `.env`.
Пока секрет не задан, вебхук отвечает 404 на всё — закрыт, а не открыт всем.
Сравнение секрета идёт постоянным временем: обычное `==` останавливается на
первом несовпавшем знаке, и по времени ответа секрет подбирается посимвольно.

Одновременно работает что-то одно: пока стоит вебхук, `getUpdates` возвращает
ошибку, поэтому перед запуском опроса вебхук снимается командой `delete`.

Токен в журнал не пишется: httpx на уровне INFO выводит полный адрес запроса,
а у Telegram токен лежит прямо в адресе — поэтому его логгер приглушён до
предупреждений.

Команды бота: `/start <код>` — привязка, `/status` — чья это учётная запись,
`/stop` — отвязать.

Рассылки собраны в `app/services/notifications.py`. Сейчас их две: новая заявка
уходит кладовщикам нужного склада, смена статуса — автору заявки. Новые события
добавляются туда же через `telegram.notify_user` и `notify_users`. Отправка идёт
после сохранения и обёрнута в перехват: сбой мессенджера не должен откатывать
заявку.

## Миграции

```bash
.venv/Scripts/alembic.exe revision --autogenerate -m "описание латиницей"
.venv/Scripts/alembic.exe upgrade head
```

Модели складывать в `app/models/` и импортировать в `app/models/__init__.py`,
иначе автогенерация их не увидит. Сообщение миграции лучше писать латиницей:
из него формируется имя файла.

### Первый администратор

Регистрации нет: сотрудников заводит администратор. На новой базе его нет ни
одного, и войти неоткуда. Поэтому при запуске приложение проверяет, есть ли хоть
один администратор, и при его отсутствии заводит учётную запись из
`SEED_OWNER_EMAIL` с паролем `SEED_OWNER_PASSWORD`.

Дальше эта учётная запись живёт обычной жизнью: пароль меняется в системе, а
переменная ни на что не влияет — существующего администратора запуск не трогает.

Со значением пароля из `.env.example` и с паролем короче восьми знаков учётная
запись не создаётся, в лог пишется ошибка: пароль из репозитория знают все, а
администратор с ним — открытая дверь.

Если учётная запись с такой почтой уже есть, но администраторов нет, ей выдаётся
роль администратора. Пароль при этом не трогается — кроме случая, когда войти по
нему нельзя (приглашение выписали, но так и не приняли): тогда пароль ставится
из переменной, иначе повышение роли не решало бы задачу.

### Когда накатывать

Схему меняем отдельным шагом, а не самим приложением по умолчанию: изменение
необратимо, откатить удалённую колонку нельзя, и решать это должен человек.

Где приложение живёт постоянным процессом — своя машина, systemd, контейнер —
удобнее иначе: `RUN_MIGRATIONS_ON_START=true`, и схема доводится до последней
ревизии при запуске. Несколько рабочих процессов стартуют одновременно, поэтому
накат идёт под `pg_advisory_lock`: первый применяет, остальные ждут и видят,
что делать нечего. Блокировка снимается при закрытии соединения, так что убитый
процесс её не оставит.

На serverless настройка игнорируется с предупреждением в логе: там процесс
поднимается на каждый запрос, а не на выкатку, и накат превратился бы в лишнюю
проверку при каждом холодном старте с риском оборваться на пределе времени.

В боевом контуре на Vercel это делает CI: задача «Миграции боевой базы» в
`.github/workflows/ci.yml` запускается после зелёных проверок при пуше в `main` —
то есть тем же пушем, которым Vercel выкатывает код. Применяется только
недостающее: когда новых миграций нет, задача ничего не делает.
Ей нужен секрет `PROD_DATABASE_URL` с **прямым** подключением — пулер в режиме
transaction ломает DDL. Пока секрет не задан, задача пропускается и сборку не
красит.

### Миграция не должна ломать работающий код

Схема и код меняются не одновременно: во время выкатки старые процессы ещё живы,
а схема уже новая. На Vercel сборка и накат идут вообще параллельно. Значит
миграция обязана оставлять предыдущую версию кода работоспособной: сначала
добавить и перенести, удалить — следующей выкаткой.

Это проверяется в CI (`tools/check_migrations.py`) для миграций, добавленных
изменением. Опасными считаются удаление колонки, таблицы, ограничения или
индекса и добавление обязательной колонки без значения по умолчанию.
Проверяется только `upgrade`: откат и должен удалять.

Когда шаг действительно нужен и совместимость продумана, это объявляется в самом
файле миграции — причина попадёт в вывод проверки:

```python
BREAKS_OLD_CODE = "колонка удаляется выкаткой позже, данные уже перенесены"
```
